实习日常0：需要提前准备起来的内容

发表于2026-05-14|更新于2026-05-14
|浏览量:

好久没有在博客里记一笔了。这章算「实习前需要主动铺好的路」：一部分是当下 AI 工程化里很实用的工具与范式，一部分是全栈技术栈上相对「Java 传统后端」思维需要补的课。支付行业部分暂时略过，后面单开一章。

一、AI Agent 开发相关：Skill、Open Spec、Superpowers、Harness、OpenClaw

日常里会看到不少围绕「如何让 AI 更可靠地干活」的基础设施：Skill 把可调用的能力与步骤固化成可被 IDE/Agent 读写的说明；各类 Harness 用来做评测、回放、约束输出；像 OpenClaw 这类项目则更接近「如何把工具链/agent 宿主」跑通。Open Spec（OpenSpec）和 Superpowers 是我自己觉得最值得先花时间吃透的两块：一个是「写什么、改什么」的规范与工作流，一个是「怎么按工程纪律来写」的合作手册。

OpenSpec：为 AI IDE 准备的规范驱动开发

可以把 OpenSpec 理解成面向 AI 原生开发场景的、规格驱动的一套实践与工具：Spec-kit 思路的进一步强化——先把「真理源」和「变更提案」说清楚，再让 AI 在边界内产出代码。

它主要解决四类问题：

  • 明确共识：动手写代码之前，先把需求与约束对齐。
  • 结构化变更：需求、任务、波及面集中在可审查的结构里。
  • 可审查输出：AI 的输出可以对照规格验收，而不是靠聊天记忆。
  • 版本控制：规格与变更可追溯，复盘和交接都轻松一截。

环境要求：Node.js ≥ 20.19.0。

Superpowers：写给 AI（和人）的工程纪律手册

Superpowers 并不替你做业务，而是一套强调工程质量与 TDD（测试驱动开发） 的协作流程：什么时候该想清楚、什么时候该隔离分支、什么时候该让子 agent 执行任务、以及如何收尾。核心工作流可以记成一串节点：

头脑风暴 → 设计确认 → 工作区隔离 → 编写计划 → 子代理开发 → 代码审查 → 分支收尾

二、全栈开发相关：Go、Node.js、React、MySQL（相对 Java 传统后端）

Node.js / Go 相对「Java 经典 Spring 后端」多出来或不一样的地方

  • 运行时与并发模型

    • Node：单线程事件循环 + 非阻塞 IO；核心是理解回调/Promise/async、事件循环阶段、别把 CPU 密集活堵在主线程；需要知道 worker_threads / child_process 何时出面。
    • Go：goroutine + channel，调度由运行时负责；要学 context 取消链路、race detector、 goroutine 泄漏与超时控制。Java 线程模型更重，惯了「线程池 + 队列」以后要换脑中图像。

  • 内存与 GC 观感
    Go 仍是带 GC 的语言，但更偏值类型与逃逸分析；Node V8 GC 和行为与 JVM 不尽相同，不能只拿「Spring Boot 内存调优直觉」套用。

  • 生态与脚手架
    Java 常被 Spring 全家桶「包干净」：依赖注入、AOP、统一配置、Starter。Node 侧更多是 小而散的库拼装（Express/Fastify、Prisma/Knex…），要自己定边界；Go 常是「标准库 + 若干精选库」，wire、fx 等可做 DI，但风格和 Spring 不尽相同。

  • 协议与部署
    gRPC/protobuf、REST、消息队列消费者在两种栈里都会出现，但打包与交付形态差异大：Docker 单行启动、静态编译二进制（Go）、与 PM2 / systemd / k8s probes（Node）的运维心智要补足。

已有 SQL 入门后，更值得往下挖的 SQL 方向（仍围绕 MySQL 场景）

在能写基本的 SELECT/JOIN/WHERE/GROUP BY 之后，可按这条线进阶：

  1. 索引与执行计划：B+ 树索引怎么选、EXPLAIN 各字段含义、覆盖索引、最左前缀、隐式类型转换导致的失效。
  2. 事务与隔离级别：READ COMMITTED / REPEATABLE READ（MySQL InnoDB 默认）下的幻象读与 Next-Key Lock 直觉；何时选乐观锁字段版本号。
  3. 锁与热点：表锁行锁粒度、SELECT ... FOR UPDATE、死锁日志怎么读、INSERT 与唯一索引冲撞。
  4. 范式与建模权衡：何时为了查询性能做反范式、冗余与一致性怎么 trade-off。
  5. 慢查询治理：分页深翻、ORDER BY 文件排序、必要时引入中间表或 ES。

分布式与锁建议在「单库事务吃透」之后串起来看：至少要分清 单机锁 vs 分布式锁（Redis/etcd、Redlock 争议）、幂等与去重键、Outbox/Inbox 这类一致性模式——否则一上微服务就很容易在「看起来像事务」的地方踩坑。

Next.js、Nuxt.js、NestJS：名字像，在后端侧的站位完全不同

框架 「后端」是什么 典型用途
Next.js React 的全栈/meta 框架：Route Handlers、Server Actions、getServerSideProps 等传统把「在同一仓库里顺便写服务端逻辑」包进来；本质是 Node 上的 HTTP/API + SSR/ISR，偏 BFF / 前后端合体。
Nuxt Vue 侧的全栈/meta 框架： server routes、server/ API：同样是 基于 Node（或 Nitro 适配的运行时），概念上和 Next 「把服务端能力嵌进前端工程」最接近。
NestJS 纯后端框架，思想接近「Node 版的 Spring」：模块化、依赖注入、装饰器路由、守卫/管道、微服务适配器。不绑定 React/Vue；和 Next/Nuxt 「页面驱动 + 顺带 API」是正交的。

一句话：想做「像样的单体/微服务后端服务」优先考虑 NestJS；想在同一项目里搞定 SSR/BFF/React 管线用 Next；Vue 语境则对照 Nuxt。 三面都绕不开「最终还是 Node HTTP、中间件与异步 IO」这层底子。
